# procurement-analytics

Аналитическая платформа по открытым данным госзакупок Казахстана
(`goszakup.gov.kz`): асинхронный загрузчик, два хранилища, оркестрация,
витрины и HTTP API поверх них.

Проект учебный и портфельный. Разделы с замерами заполняются по мере
прохождения этапов — пустых обещаний в README нет, только то, что измерено.

## Статус

| Этап | Что | Статус |
|---|---|---|
| 1 | Асинхронный загрузчик | готов |
| 2 | PostgreSQL + ClickHouse | готов |

| 4 | Аналитический слой | готов |
| 5 | FastAPI | готов |
| 6 | Тесты и профилирование | готов |

## Источник данных

REST v3 `https://ows.goszakup.gov.kz/v3`, авторизация `Bearer`-токеном.
Пагинация курсорная: `limit` + `page=next&search_after=<id>`, ответ несёт
готовую ссылку `next_page`. Сущности первой очереди — `contracts` и `lots`.

Явных рейт-лимитов документация не декларирует, поэтому загрузчик не
предполагает известный порог, а подстраивает конкурентность по ответам 429.
Проект уважает лимиты публичного сервиса: у CLI есть ограничитель числа
страниц, конкурентность по умолчанию низкая.

Без токена проект работает на локальных фикстурах
(`PA_SOURCE__KIND=fixtures`).

## Стек

Python 3.12, asyncio, httpx, FastAPI, Pydantic v2, SQLAlchemy 2.x (async),
Alembic, PostgreSQL, ClickHouse, Airflow, pytest + pytest-asyncio +
testcontainers + respx, Docker Compose, py-spy.

## Загрузчик

```
python -m procurement.ingest.cli --entity contracts --max-pages 3 --out data/contracts.jsonl
```

Без токена работает на локальных фикстурах. Что умеет: курсорная пагинация,
адаптивная конкурентность (сжимается на 429, восстанавливается в тишине),
повторы с экспоненциальной паузой и джиттером, очередь с ограничением размера
между загрузкой и обработкой, общий бюджет времени, мягкая остановка по
SIGTERM с сохранением позиции. Перезапуск продолжает с сохранённого курсора и
не дублирует уже загруженное.

Ход работы с разбором решений — в [девлоге](docs/devlog.md).

## Оркестрация

Два DAG-а в [dags/](dags/):

- `backfill_contracts` — помесячная выкачка, один запуск на месяц, `catchup=True`;
- `sync_contracts` — догрузка изменений по водяному знаку, ежечасно.

Логики в DAG-ах нет: они вызывают обычные функции из `procurement.jobs`, которые
запускаются и без оркестратора:

```
python -m procurement.jobs.cli backfill --entity contracts --from 2023-01 --to 2025-12
```

Поднять Airflow (интерфейс на http://localhost:8080):

```
make airflow-up
```

**Идемпотентность.** Повторный бэкфилл за тот же месяц не задваивает данные.
Месяц собирается во временную таблицу и въезжает в боевую через
`ALTER TABLE ... REPLACE PARTITION` — одним неделимым действием. Проверено
прогоном трижды подряд и закреплено тестом.

**Проверки качества** стоят между загрузкой и публикацией: пустые обязательные
поля, суммы вне диапазона, дубли по id, нераспознанные даты и расхождение с
числом записей, заявленным источником. Не прошли проверку уровня fail —
партиция не подменяется, испорченный месяц до витрин не доезжает.

## API

```
make api
```

Документация ручек — http://localhost:8000/docs

| Ручка | Что отдаёт |
|---|---|
| `GET /health/live` | процесс жив (зависимости не проверяет намеренно) |
| `GET /health/ready` | готов принимать запросы, с состоянием каждой базы |
| `GET /v1/customers/{bin}/suppliers` | поставщики заказчика и их доли |
| `GET /v1/suppliers/{biin}/customers` | заказчики поставщика и их доли |
| `GET /v1/categories` | свёртка сумм лотов на выбранный уровень классификатора |
| `GET /v1/contracts/monthly` | помесячная динамика с изменением к предыдущему месяцу |
| `GET /v1/lots/price-outliers` | лоты с наибольшим отклонением цены от медианы позиции |
| `GET /v1/customers/concentration` | индекс Херфиндаля и доля первых поставщиков |
| `GET /v1/suppliers/{biin}/activity` | периоды непрерывной активности |

Пагинация без `COUNT` по всей выборке: запрашивается на запись больше, чем
нужно, и по ней определяется наличие следующей страницы. Ошибки приходят в
едином конверте с машиночитаемым кодом.

Задержки на 1.8 млн договоров — [docs/bench/api_latency.md](docs/bench/api_latency.md).
Помесячные ручки ускорены витриной с 238 до 22 мс.

## Аналитические запросы

Шесть запросов, каждый в двух вариантах — [sql/postgres/](sql/postgres/) и
[sql/clickhouse/](sql/clickhouse/):

| Запрос | Приём |
|---|---|
| Свёртка по дереву классификатора | рекурсивный CTE, свёртка на любой уровень |
| Доля поставщика в закупках заказчика | `SUM() OVER (PARTITION BY)` поверх агрегата |
| Отклонение цены лота от медианы позиции | медиана по товарной позиции, цена за единицу |
| Помесячная динамика | `LAG` для сравнения с предыдущим периодом |
| Концентрация закупок (индекс Херфиндаля) | два этажа оконных функций, накопительная доля |
| Периоды непрерывной активности | gaps and islands через разность номеров |

Замеры и разбор — [docs/bench/sql_comparison.md](docs/bench/sql_comparison.md).
Оба варианта каждого запроса сверяются построчно: сравнивать скорость без
сверки результата бессмысленно.

## Архитектура

```
goszakup REST v3
      │
      ▼
  загрузчик (asyncio, httpx)
      │
      ├──────────────► PostgreSQL   состояние, журнал, справочники, пользователи
      │
      ▼
  ClickHouse                        факты: договоры и лоты
      │
      ▼
  витрины -> FastAPI
```

### Почему два хранилища, а не одно

Данные в проекте распадаются на два вида с противоположными требованиями.

**Состояние и справочники.** Курсоры, водяные знаки, журнал запусков,
пользователи, сохранённые фильтры. Объём — тысячи строк. Меняются по одной,
часто, и требуют честных транзакций: если прогон записал курсор, но не записал
строку журнала, дальше жить нельзя. Нужны внешние ключи, ограничения
уникальности и откат. Это ровно то, для чего сделан PostgreSQL.

**Факты.** Договоры и лоты: миллионы записей за несколько лет. Построчно не
меняются — приходят ревизиями. Читаются не по одной, а агрегатами по большим
диапазонам: суммы по заказчику за год, доли поставщиков, медианы цен. Строчное
хранение здесь проигрывает: чтобы просуммировать одну колонку, PostgreSQL
поднимет с диска все остальные. ClickHouse хранит по колонкам и читает только
нужные.

Сложить всё в PostgreSQL можно, и на миллионе строк разницы не заметно. На
двадцати миллионах она измерима: полный свод по заказчикам в ClickHouse
занимает [179 мс](docs/bench/order_by.md). Сложить всё в ClickHouse нельзя:
там нет внешних ключей, а транзакции устроены так, что рассчитывать на них для
состояния синхронизации не выйдет.

### PostgreSQL

Схема ведётся Alembic с нуля, миграции автогенерируются из моделей SQLAlchemy
2.x. Имена ограничений заданы соглашением, поэтому автогенерация видит
расхождения, а не предлагает пересоздать всё подряд. Проверка на дрейф —
`alembic check`.

### ClickHouse

Факты лежат в `ReplacingMergeTree` с версией по дате изменения: записи
ревизируются, и движок при слиянии оставляет свежую версию.

Ключ сортировки выбран экспериментом на 20 млн записей, четыре варианта —
[docs/bench/order_by.md](docs/bench/order_by.md). Победил
`(customer_bin, supplier_biin, id)`.

Про `FINAL` коротко: он даёт верный ответ, но на 20 млн строк с 2 млн ревизий
стоит **7.5 раза** (172 мс против 1300 мс, замер воспроизводится
`scripts/demo_final.py`). Подробный разбор, почему на него нельзя опираться в
проде, — в [девлоге](docs/devlog.md).

## Замеры

- [Выбор ключа сортировки в ClickHouse](docs/bench/order_by.md) — 4 варианта на 20 млн записей.
- Цена `FINAL`: 172 мс против 1300 мс на 20 млн строк с 2 млн ревизий.
- **[Задержки API](docs/bench/api_latency.md)** на 1.8 млн договоров: от 7 мс
  (проба готовности) до 641 мс (концентрация закупок). Витрина ускорила
  помесячные ручки в 11 раз.
- **[Аналитика: PostgreSQL против ClickHouse](docs/bench/sql_comparison.md)** на
  1.8 млн договоров и 1.8 млн лотов. ClickHouse быстрее в 3.6–57 раз в
  зависимости от запроса; на диске 158.7 МиБ против 741 МБ.
- **Бэкфилл за 3 года: 1 800 000 записей за 126.4 с, 14 237 строк/с.** 36 месяцев,
  36 партиций, 85.6 МиБ на диске, ноль дублей. До профилирования тот же бэкфилл
  занимал 202.7 с (8881 строк/с). Данные синтетические — токена goszakup пока
  нет, — но замер относится к конвейеру и заливке, а не к сети.
- **[Профилирование загрузчика](docs/bench/profiling.md)**: py-spy показал, что
  51 % процессорного времени уходит на `datetime.strptime`. Замена на
  `fromisoformat` — **+66 % пропускной способности** на изолированном прогоне
  (34 212 против 56 690 строк/с). Там же: подбор размера батча, режим отладки
  asyncio, orjson против json.

## Что бы я сделал иначе

**Профилировал бы на первом этапе, а не на шестом.** Ключ сортировки в
ClickHouse я выбирал замером — и не пожалел. А разбор дат написал «как
принято», и он полгода проекта съедал половину процессорного времени
загрузчика. Правило простое: если код выполняется на каждой записи, его цену
надо узнать сразу, а не после того, как поверх него написано ещё пять этапов.

**Не брал бы pydantic для `Page` и `Batch`.** Это внутренние структуры, они не
приходят снаружи и проверять в них нечего: `RawRecord` объявлен как
`dict[str, Any]`. Валидация работает на каждой странице и каждом батче и стоит
9 % профиля. `dataclass` хватило бы. Менять сейчас дороже, чем не заводить
тогда: `Page` попадает в сохраняемое состояние курсора.

**Сверялся бы со схемой источника до написания фикстур.** В первых фикстурах я
описал поле `fin_year`, которого у договоров нет вовсе. Ошибка вскрылась только
на сверке с GraphQL-схемой на четвёртом этапе — то есть три этапа тесты
проверяли выдуманную форму данных. Полчаса чтения схемы в начале сэкономили бы
день переделок.

**Партиционировал бы лоты по дате, а не по `intDiv(id, 5000000)`.** У лотов в
API нет ни одной неизменной даты, и я взял идентификатор. Работает, но
`REPLACE PARTITION` по месяцам для лотов невозможен, и это ограничение тянется
дальше по всему проекту. Правильный путь был обогатить лот датой объявления из
`TrdBuy` на этапе загрузки — дороже на входе, зато без ограничения на выходе.

**Писал бы проверки качества вместе с загрузчиком.** Они появились на третьем
этапе, и всё, что загружалось до этого, проверялось глазами. Две ошибки
(водяной знак, который молча не сохранялся, и бесконечный цикл на декабре)
дожили до момента, когда их стало дороже искать.

## Оговорка по выводам

Формулировки в аналитических выводах — фактические. «Доля поставщика в
закупках заказчика — 94%» — это результат расчёта. Утверждения о сговоре или
схемах из этих данных не следуют и в проекте не делаются.
