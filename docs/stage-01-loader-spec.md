# Этап 1 — ТЗ на загрузчик

Статус: в работе. Код пишет автор проекта, эта страница — постановка.

## Контекст источника (проверено по документации)

- REST v3: `https://ows.goszakup.gov.kz/v3`
- Авторизация: заголовок `Authorization: Bearer <token>`
- Пагинация курсорная: `limit` + `page=next&search_after=<id последнего документа>`.
  В теле ответа приходит готовая ссылка `next_page`.
- Значение по умолчанию `limit` — 50.
- Явных рейт-лимитов в документации нет. Порог нащупываем сами по ответам 429,
  поэтому конкурентность обязана быть адаптивной, а не константной.
- Сущности первого этапа: `contracts`, `lots`.

Токена пока нет, поэтому источник за интерфейсом и переключается настройкой
`PA_SOURCE__KIND` (`fixtures` / `rest`). Весь загрузчик и все тесты первого
этапа пишутся против фикстур и respx; появление токена не должно требовать
правок в коде конвейера.

## Что должно получиться

Одна команда, которая выкачивает сущность целиком, кладёт сырые записи
батчами дальше по конвейеру, переживает 429 и 5xx, корректно останавливается
по SIGTERM и при следующем запуске продолжает с сохранённой позиции.

## Границы модулей

```
src/procurement/ingest/
├── models.py       # Pydantic v2: Page, RawRecord, Batch, CursorState
├── source.py       # протокол источника: fetch_page(entity, cursor) -> Page
├── rest_source.py  # реализация поверх httpx.AsyncClient
├── fixture_source.py
├── limiter.py      # адаптивная конкурентность
├── retry.py        # политика повторов
├── pipeline.py     # producer -> asyncio.Queue -> consumers
├── state.py        # чтение/запись курсора (этап 1 — файл, этап 2 — PostgreSQL)
└── cli.py          # точка входа
```

Границы держим жёстко: `pipeline.py` не знает про httpx, `rest_source.py` не
знает про очередь. Иначе на этапе 6 не получится подменить источник в тестах.

### `source.py`

Протокол (`typing.Protocol`), один обязательный метод:

```
async def fetch_page(self, entity: str, cursor: str | None) -> Page
```

`Page` несёт: список сырых записей, курсор следующей страницы (`None` — конец),
общее количество записей по мнению API (нужно на этапе 3 для сверки), и
отметку времени ответа.

Решение, которое надо принять осознанно: пробрасывает ли источник наружу
HTTP-специфику (код ответа, `Retry-After`). Мой совет — не пробрасывать, а
поднимать доменные исключения (`SourceRateLimited(retry_after)`,
`SourceUnavailable`, `SourceBadResponse`), иначе слой повторов окажется завязан
на httpx и не переживёт добавление GraphQL.

### `limiter.py` — адаптивная конкурентность

`asyncio.Semaphore` создаётся с фиксированным числом слотов и не умеет
изменяться на лету. Значит, нужна обёртка, которая держит целевое значение и
регулирует фактическое число доступных слотов.

Требования:
- старт с `concurrency_start`, границы `concurrency_min`..`concurrency_max`;
- на 429 — уменьшение (множителем, не на единицу);
- после серии успешных ответов — плавное восстановление (прибавка по одному);
- восстановление не должно начинаться сразу после 429, нужен период тишины;
- лимитер обязан быть корректен при отмене: захваченный слот освобождается
  в любом исходе.

Способ хранения «лишних» слотов при уменьшении — твоё проектное решение.
Подсказка: слот можно не возвращать в семафор, а «съесть», и тогда
восстановление — это возврат съеденных слотов.

### `retry.py`

Повторяем на: 429, 5xx, `httpx.TimeoutException`, `httpx.ConnectError`,
обрыв соединения при чтении тела.
Не повторяем на: 400, 401, 403, 404 и на ошибках валидации Pydantic.

Пауза: экспонента от `retry_base_delay_s`, потолок `retry_max_delay_s`,
обязательный джиттер. Если пришёл `Retry-After` — он главнее расчётной паузы.

Вопрос, на который надо ответить до написания кода: джиттер полный
(`random(0, delay)`) или децентрированный (`delay * random(0.5, 1.5)`), и что
из этого лучше расталкивает одновременно проснувшиеся корутины.

### `pipeline.py`

Producer читает страницы последовательно по курсору и кладёт батчи в
`asyncio.Queue(maxsize=queue_maxsize)`. Consumers разбирают и валидируют.

Курсорная пагинация последовательна по определению: следующий курсор известен
только из текущего ответа. Значит, конкурентность внутри одной сущности взять
неоткуда — подумай, где она тогда вообще появляется (подсказка: сущностей две,
и у этапа 3 есть помесячный бэкфилл).

Backpressure: `maxsize` на очереди — единственное, что не даёт producer'у
выкачать всю сущность в память, пока парсер отстаёт. Значение подбирается
замерами на этапе 6, не «на глаз».

Общий бюджет времени — `asyncio.timeout(overall_timeout_s)` вокруг всего
прогона. Таймаут на отдельный запрос задаётся в httpx и не заменяет общий.

### Отмена

По SIGTERM (и SIGINT) прогон обязан:
1. перестать запрашивать новые страницы;
2. дописать батч, который уже в работе;
3. сохранить курсор последней **полностью обработанной** страницы;
4. выйти с ненулевым кодом, отличимым от кода падения.

`finally` в корутине при отмене выполняется, но `await` внутри `finally`
может быть отменён повторно. Это ловушка — разберись, как её обходят
(`asyncio.shield`) и почему шилдить весь конвейер нельзя.

Отдельно: сохранять курсор нужно **после** успешной обработки страницы, а не
после её получения. Разница — в том, потеряются данные при падении или
задвоятся. Задвоение переживаемо (записи идемпотентны по id), потеря — нет.

### `state.py`

На этапе 1 — JSON-файл, атомарная запись через временный файл и `os.replace`.
На этапе 2 переедет в PostgreSQL без смены интерфейса. Хранится: сущность,
курсор, watermark по дате изменения, время последнего успешного прогона,
счётчики.

### `cli.py`

```
python -m procurement.ingest.cli --entity contracts --max-pages 10
```

Флаги: `--entity`, `--max-pages` (ограничитель для отладки — на публичный
сервис без него не ходим), `--from-scratch` (игнорировать сохранённый курсор),
`--dry-run`.

## Критерии приёмки

1. `make lint`, `make type`, `make test-unit` — зелёные.
2. Прогон на фикстурах в 3 страницы даёт ровно столько записей, сколько в
   фикстурах, без дублей по id.
3. Тест на respx: первые два запроса отдают 429 с `Retry-After`, третий — 200.
   Загрузчик доходит до конца, число попыток совпадает с ожидаемым,
   конкурентность после 429 уменьшилась.
4. Тест на отмену: отменяем прогон на середине, проверяем, что файл состояния
   содержит курсор последней полностью обработанной страницы, а не следующей.
5. Перезапуск после отмены дочитывает остаток и не дублирует уже полученное.
6. Тест на общий таймаут: источник отдаёт страницы медленнее бюджета, прогон
   завершается по `asyncio.timeout`, курсор сохранён.

## Что продумать самому до первой строчки кода

1. Где граница ответственности между `retry.py` и `limiter.py` — кто именно
   реагирует на 429 и в каком порядке.
2. Что считать «единицей работы» для сохранения курсора: страница или батч.
3. Как отличить конец данных от пустой страницы посреди выдачи.
4. Что делать, если API вернул курсор, который уже встречался (защита от
   бесконечного цикла).
5. Сколько `httpx.AsyncClient` на прогон и почему не по одному на запрос.
6. Кто закрывает очередь и как consumers узнают, что producer закончил —
   sentinel или отдельный флаг; что произойдёт при N consumers.
7. Что случится, если consumer упадёт с исключением, а producer продолжит
   писать в очередь.
8. Почему `asyncio.Queue` без `maxsize` в этой задаче — скрытая утечка памяти.
