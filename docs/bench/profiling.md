# Профилирование загрузчика

Замер от 2026-09-28. Машина: Windows 11, Python 3.12.10, ClickHouse 24.8 в
Docker на той же машине. Всё воспроизводится:

```
.venv/Scripts/python scripts/profile_loader.py --records 50000
.venv/Scripts/python scripts/bench_json.py
.venv/Scripts/py-spy record --subprocesses --rate 250 --format raw -o docs/bench/loader_folded_after.txt -- .venv/Scripts/python scripts/profile_loader.py --records 200000
.venv/Scripts/python scripts/fold_summary.py docs/bench/loader_folded_after.txt
```

## Итог одной строкой

Половина процессорного времени загрузчика уходила на `datetime.strptime`.
Замена на `datetime.fromisoformat` дала **+66 % пропускной способности** на
изолированном прогоне и сократила трёхлетний бэкфилл со **202.7 с до 126.4 с**.

## Оговорки, без которых цифры врут

**Стенд искажает профиль.** Синтетический источник не получает записи, а
придумывает их: `random`, `strftime`, форматирование строк. Настоящий REST
ничего такого не делает. Профиль под этим источником показывает работу стенда.
Поэтому в `scripts/profile_loader.py` есть второй источник — `replay`:
страницы сериализуются в JSON один раз **до** замера, а в замер попадает то,
чем занят боевой источник за вычетом сети, то есть `orjson.loads` и сборка
`Page`. Все выводы ниже сделаны на нём.

**Часов Windows хватает не на всё.** `asyncio` берёт время через
`time.monotonic()`, а это на Windows `GetTickCount64()` с разрешением
15.625 мс:

```
>>> time.get_clock_info('monotonic')
namespace(implementation='GetTickCount64()', resolution=0.015625, ...)
```

Отсюда два следствия. Режим отладки asyncio не увидит блокировок короче
15.6 мс, и все его цифры кратны этой величине. Замеры пропускной способности
этим не затронуты: там `time.perf_counter()`, у него `QueryPerformanceCounter`
с разрешением 0.1 мкс.

**Сеть не участвует.** ClickHouse стоит на той же машине. В бою к каждой
вставке добавится сетевая задержка, и доля драйвера вырастет.

## Из чего складывается время: четыре угла стенда

50 000 записей, страница 500, батч 500, медиана из трёх прогонов.

| Источник | Приёмник | Строк/с | Что меряем |
|---|---|---|---|
| replay | null | **458 426** | сам конвейер: очередь, батчи, курсор |
| synthetic | null | 59 095 | то же плюс выдумывание записей |
| replay | clickhouse | 54 028 | конвейер плюс запись в хранилище |
| synthetic | clickhouse | 30 972 | как в бэкфилле сегодня |

Первая строка отвечает на вопрос, который стоило задать до всякой
оптимизации: **конвейер сам по себе ничего не стоит**. 458 тысяч строк в
секунду — это в восемь раз быстрее, чем всё остальное вместе. Ускорять очередь,
подбирать число воркеров или переписывать `OrderedCommitter` было бы работой
впустую.

Вторая строка — цена стенда: генератор записей дороже разбора JSON в 7.8 раза.
Ровно поэтому профилировать под ним нельзя.

## py-spy: как он вообще заработал

`py-spy record -- .venv/Scripts/python script.py` падал:

```
Error: Failed to find python version from target process
```

Тот же py-spy на системном интерпретаторе работал. Значит дело не в версии
Python и не в правах. Список процессов во время прогона:

```
ProcessId ParentProcessId ExecutablePath
    69108            9256 ...\.venv\Scripts\python.exe
    57424           69108 ...\Programs\Python\Python312\python.exe
```

`python.exe` внутри venv на Windows — не интерпретатор, а **запускала**: она
порождает настоящий интерпретатор отдельным процессом. Размеры файлов это
подтверждают: 274 424 байта у запускалы против 104 952 у настоящего
`python.exe`. py-spy цеплялся к запускале, Python в ней не находил и честно об
этом сообщал.

Лечится флагом `--subprocesses`, который велит спускаться по дереву процессов.

Вывод на будущее: сообщение об ошибке было точным, неверным было моё
предположение о том, к чему присоединяется профилировщик.

## Профиль до: половина времени в разборе дат

200 000 записей, частота срезов 250 Гц, 3 472 среза. Доли внутри прогона
конвейера (подготовка стенда отброшена):

| Область | Доля |
|---|---|
| сборка строк для ClickHouse (`to_rows`) | 58.9 % |
| **из них разбор дат (`as_datetime`)** | **51.2 %** |
| драйвер ClickHouse: сеть и сериализация | 19.8 % |
| модели pydantic (`Page`/`Batch`) | 5.9 % |

Листья показывают то же самое крупным планом: `as_datetime` 8.8 %, дальше
подряд `_strptime` в шести разных строках и `locale.getlocale` 4.7 %.

Последнее и есть объяснение. `datetime.strptime` разбирает строку формата
заново при каждом вызове и по дороге спрашивает локаль — на запись приходится
три даты, на страницу полторы тысячи вызовов.

## Замер вариантов разбора

Строка `"2024-06-11 10:00:00"`, медиана из семи прогонов по 1000 значений:

| Способ | Время | Отношение |
|---|---|---|
| `strptime` по списку форматов (как было) | 4.45 мкс | 1.0 |
| ручная нарезка по позициям + `datetime(...)` | 0.80 мкс | 5.6× |
| **`fromisoformat`** | **0.43 мкс** | **10.3×** |

Ручная нарезка проиграла тому, что уже есть в стандартной библиотеке:
`fromisoformat` написан на C под заранее известную форму строки. Писать своё
не понадобилось.

Заодно поведение стало правильнее. Прежняя версия принимала три формата и на
всём остальном молча возвращала `UNKNOWN_DATE` — то есть **теряла настоящую
дату**, не сообщая об этом. Новая принимает ISO-8601 целиком: дробные доли
секунды, смещение пояса. Смещение при этом переводится в UTC, а не затирается;
затереть означало бы сдвинуть время на величину смещения и не заметить. Для
`ReplacingMergeTree`, который выбирает версию записи по `last_update_date`,
такой сдвиг — это выбор не той версии.

Список форматов остался запасным путём: `fromisoformat` покрывает всё, что
источник присылает сегодня, а список — место, куда добавлять формы, когда они
появятся. Там цена `strptime` уже неважна.

## Профиль после

| Область | Было | Стало |
|---|---|---|
| разбор дат (`as_datetime`) | 51.2 % | **11.2 %** |
| сборка строк (`to_rows`) | 58.9 % | 26.0 % |
| драйвер ClickHouse | 19.8 % | **34.9 %** |
| модели pydantic | 5.9 % | 9.0 % |

Узкое место переехало из нашего кода в драйвер — это и есть признак того, что
оптимизация закончена. Дальше ускорять надо либо отказом от лишней работы,
либо другим протоколом вставки, а не подкруткой наших функций.

## Размер батча

50 000 записей, источник replay, приёмник ClickHouse, медиана из трёх
прогонов. Батч нарезается **внутри страницы**, поэтому больше размера
страницы он быть не может, и таблиц две.

Страница 500 (как в бою):

| Батч | Строк/с | Вставок |
|---|---|---|
| 50 | 2 181 | 1000 |
| 100 | 6 077 | 500 |
| 250 | 35 094 | 200 |
| **500** | **53 831** | 100 |

Страница 10 000 (чтобы посмотреть, что дальше):

| Батч | Строк/с | Вставок |
|---|---|---|
| 500 | 48 872 | 100 |
| 1 000 | 73 281 | 50 |
| 2 500 | 87 262 | 20 |
| 5 000 | 94 540 | 10 |
| 10 000 | 99 461 | 5 |

Время определяется **числом вставок, а не числом строк**. Проверка, которая
это подтверждает: тот же батч 50 с приёмником `null` даёт 414 239 строк/с и
не колеблется между прогонами вовсе. Значит ни конвейер, ни нарезка к цене
отношения не имеют — вся она в пути до хранилища.

Сервер при этом почти не при чём. По `system.query_log` средняя вставка
занимает **1.48 мс** при 12 255 вставках. На тысяче вставок это полторы
секунды серверного времени против 8–24 секунд по часам. Остальное — накладные
расходы клиента на каждый запрос: сборка контекста вставки, сериализация,
обращение по HTTP.

**Проверенная и не подтвердившаяся догадка.** Первое объяснение звучало как
«ClickHouse притормаживает вставки, когда кусков становится много»: 1000
вставок дают 1000 кусков в одной партиции. Проверил вместо того, чтобы
поверить: порог `parts_to_delay_insert` равен 1000, а счётчиков задержанных
вставок в `system.events` нет вовсе — то есть торможение ни разу не включалось.
Объяснение отброшено.

Что осталось необъяснённым: на батчах 50 и 100 разброс между прогонами
достигает трёхкратного (2 065 … 5 688 строк/с), тогда как на 500 и больше
прогоны совпадают с точностью до процентов. До корня этого я не дошёл.

**Что с этим делать.** Ничего. Наш `page_limit` ограничен пятьюстами, батч
нарезается внутри страницы, значит в бою больше 500 не бывает. Чтобы
добраться до полки в 100 тысяч строк/с, батчи пришлось бы копить через
границы страниц, а это ломает главное свойство `OrderedCommitter`: батч
принадлежит странице, и курсор двигается строго по порядку страниц. Платить
таким свойством за ×1.8 нельзя — тем более что в бою узкое место не здесь.
Простая оценка: 100 страниц по 200 мс сетевой задержки при четырёх
одновременных запросах — это 5 секунд на 50 000 записей, то есть 10 000
строк/с. Запись на 54 тысячах строк/с в эту цифру не упирается.

## Режим отладки asyncio

`asyncio.run(..., debug=True)` плюс `loop.slow_callback_duration` заставляет
цикл ругаться на обработчики, которые держали его дольше порога. Порог взят
0.02 с — ниже разрешения часов Windows опускаться бессмысленно.

Боевая настройка, батч 500, 100 страниц — два предупреждения за весь прогон:

```
main.<locals>.wrapped()   0.906 с
Pipeline._produce()       0.047 с
```

Первое — **сам стенд**: `ReplaySource` сериализует страницы синхронно внутри
корутины. Режим отладки нашёл настоящую блокировку, и она оказалась в
измерительном коде, а не в загрузчике. Второе срабатывает один раз за прогон,
на первой странице.

С батчем 10 000 картина другая: `Pipeline._handle` регулярно занимает цикл на
31–47 мс. Это `to_rows` и сериализация десяти тысяч записей — синхронная
работа, во время которой ни одна другая страница не движется. Ещё один довод
против больших батчей, помимо `OrderedCommitter`.

Все значения кратны 15.6 мс: 0.031, 0.047, 0.094. Разрешение часов видно прямо
в выводе.

## orjson против json

Медиана из семи прогонов, страница 500 записей.

| Операция | json | orjson | Отношение |
|---|---|---|---|
| `loads` договоров (179.7 КиБ) | 0.793 мс | 0.549 мс | 1.4× |
| `loads` лотов (150.0 КиБ, кириллица) | 0.901 мс | 0.390 мс | 2.3× |
| `dumps` договоров | 0.793 мс | 0.109 мс | **7.3×** |
| `dumps` лотов | 0.825 мс | 0.091 мс | **9.1×** |

На разборе выигрыш скромный, на сборке — семикратный. Разница между
договорами и лотами объясняется кириллицей: `json` по умолчанию экранирует
не-ASCII в `\uXXXX`, и путь с `ensure_ascii=False` в нём заметно медленнее.

**Честный вывод: для загрузчика это не имеет значения.** Разбор страницы стоит
0.55 мс против 0.79 мс — на фоне сетевого запроса в десятки миллисекунд
разница теряется. В профиле после оптимизации весь разбор ответа занимает
8.2 % — и это на стенде без сети; с настоящим API доля будет около нуля.

Где orjson действительно нужен, так это на сборке: выгрузка в jsonl и
подготовка фикстур. Там семикратная разница видна.

Оставляем orjson: он уже стоит, ничего не стоит держать и на сборке
выигрывает. Но выдавать его за оптимизацию загрузчика было бы неправдой.

## Что дальше

Из профиля после оптимизации видны следующие кандидаты, все мелкие:

**`as_decimal`, 4.5 % листьев.** Идёт через `Decimal(str(value))` — это
сознательное решение против `Decimal(0.1) == 0.1000000000000000055`. Дешевле
было бы принимать целые копейки целым числом, но это меняет схему.

**Модели pydantic, 9 %.** `Page` и `Batch` проверяются на каждой странице и
каждом батче. Проверка списка словарей ничего не даёт: `RawRecord` — это
`dict[str, Any]`, проверять там нечего. Заменить на `dataclass` было бы
честнее, но `Page` сериализуется в состояние, и переделка затронет хранение
курсора.

**Драйвер, 34.9 %.** Настоящий следующий шаг. Сейчас записи уходят списками
списков, драйвер раскладывает их по колонкам сам. Колоночная подача
(`column_oriented=True`) должна убрать часть работы. Не проверено, цифр нет —
поэтому и не сделано.
