# procurement-analytics

Аналитическая платформа по открытым данным госзакупок Казахстана
(`goszakup.gov.kz`): асинхронный загрузчик, два хранилища, оркестрация,
витрины и HTTP API поверх них.

Проект учебный и портфельный. Разделы с замерами заполняются по мере
прохождения этапов — пустых обещаний в README нет, только то, что измерено.

## Статус

| Этап | Что | Статус |
|---|---|---|
| 1 | Асинхронный загрузчик | готов |
| 2 | PostgreSQL + ClickHouse | готов |
| 3 | Airflow: инкремент и бэкфилл | следующий |
| 4 | Аналитический слой | не начат |
| 5 | FastAPI | не начат |
| 6 | Тесты и профилирование | не начат |

## Источник данных

REST v3 `https://ows.goszakup.gov.kz/v3`, авторизация `Bearer`-токеном.
Пагинация курсорная: `limit` + `page=next&search_after=<id>`, ответ несёт
готовую ссылку `next_page`. Сущности первой очереди — `contracts` и `lots`.

Явных рейт-лимитов документация не декларирует, поэтому загрузчик не
предполагает известный порог, а подстраивает конкурентность по ответам 429.
Проект уважает лимиты публичного сервиса: у CLI есть ограничитель числа
страниц, конкурентность по умолчанию низкая.

Без токена проект работает на локальных фикстурах
(`PA_SOURCE__KIND=fixtures`).

## Стек

Python 3.12, asyncio, httpx, FastAPI, Pydantic v2, SQLAlchemy 2.x (async),

## Загрузчик

```
python -m procurement.ingest.cli --entity contracts --max-pages 3 --out data/contracts.jsonl
```

Без токена работает на локальных фикстурах. Что умеет: курсорная пагинация,
адаптивная конкурентность (сжимается на 429, восстанавливается в тишине),
повторы с экспоненциальной паузой и джиттером, очередь с ограничением размера
между загрузкой и обработкой, общий бюджет времени, мягкая остановка по
SIGTERM с сохранением позиции. Перезапуск продолжает с сохранённого курсора и
не дублирует уже загруженное.

Ход работы с разбором решений — в [девлоге](docs/devlog.md).

## Архитектура

```
goszakup REST v3
      │
      ▼
  загрузчик (asyncio, httpx)
      │
      ├──────────────► PostgreSQL   состояние, журнал, справочники, пользователи
      │
      ▼
  ClickHouse                        факты: договоры и лоты
      │
      ▼
  витрины -> FastAPI
```

### Почему два хранилища, а не одно

Данные в проекте распадаются на два вида с противоположными требованиями.

**Состояние и справочники.** Курсоры, водяные знаки, журнал запусков,
пользователи, сохранённые фильтры. Объём — тысячи строк. Меняются по одной,
часто, и требуют честных транзакций: если прогон записал курсор, но не записал
строку журнала, дальше жить нельзя. Нужны внешние ключи, ограничения
уникальности и откат. Это ровно то, для чего сделан PostgreSQL.

**Факты.** Договоры и лоты: миллионы записей за несколько лет. Построчно не
меняются — приходят ревизиями. Читаются не по одной, а агрегатами по большим
диапазонам: суммы по заказчику за год, доли поставщиков, медианы цен. Строчное
хранение здесь проигрывает: чтобы просуммировать одну колонку, PostgreSQL
поднимет с диска все остальные. ClickHouse хранит по колонкам и читает только
нужные.

Сложить всё в PostgreSQL можно, и на миллионе строк разницы не заметно. На
двадцати миллионах она измерима: полный свод по заказчикам в ClickHouse
занимает [179 мс](docs/bench/order_by.md). Сложить всё в ClickHouse нельзя:
там нет внешних ключей, а транзакции устроены так, что рассчитывать на них для
состояния синхронизации не выйдет.

### PostgreSQL

Схема ведётся Alembic с нуля, миграции автогенерируются из моделей SQLAlchemy
2.x. Имена ограничений заданы соглашением, поэтому автогенерация видит
расхождения, а не предлагает пересоздать всё подряд. Проверка на дрейф —
`alembic check`.

### ClickHouse

Факты лежат в `ReplacingMergeTree` с версией по дате изменения: записи
ревизируются, и движок при слиянии оставляет свежую версию.

Ключ сортировки выбран экспериментом на 20 млн записей, четыре варианта —
[docs/bench/order_by.md](docs/bench/order_by.md). Победил
`(customer_bin, supplier_biin, id)`.

Про `FINAL` коротко: он даёт верный ответ, но на 20 млн строк с 2 млн ревизий
стоит **7.5 раза** (172 мс против 1300 мс, замер воспроизводится
`scripts/demo_final.py`). Подробный разбор, почему на него нельзя опираться в
проде, — в [девлоге](docs/devlog.md).

## Оговорка по выводам

Формулировки в аналитических выводах — фактические. «Доля поставщика в
закупках заказчика — 94%» — это результат расчёта. Утверждения о сговоре или
схемах из этих данных не следуют и в проекте не делаются.
