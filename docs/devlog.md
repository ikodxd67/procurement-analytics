# 20 сентября 2026 — окружение

## Что было на входе

Пустая машина под Windows 11. Установлен только Python 3.14, Docker Desktop
установлен но выключен, виртуального окружения нет.

## Python 3.12 вместо 3.14

В `pyproject.toml` версия зафиксирована как `>=3.12,<3.13`, и в CI стоит 3.12.
Писать код на 3.14 при такой настройке значит проверять одно, а запускать
другое: расхождение вылезет не у тебя, а на сервере.

Вторая причина практическая. Под каждую версию Python библиотеки собираются
отдельно. При установке видны имена вида `lz4-4.4.5-cp312-cp312-win_amd64.whl`,
где `cp312` означает «для Python 3.12». Под самую свежую версию таких готовых
пакетов часто ещё нет, и pip начинает собирать из исходников — на Windows это
обычно кончается ошибкой про отсутствующий компилятор.

Ставили через `winget install --id Python.Python.3.12 --scope user`. Область
`user` выбрана, чтобы не требовались права администратора и не трогался
системный Python.

`.venv` — обычная папка, в которой лежит своя копия интерпретатора и свой

Проверка, которая это показывает:

```
глобальный:  ModuleNotFoundError: No module named 'httpx'
из .venv:    httpx есть, 0.28.1
```

Одна и та же команда, разный результат.

## Editable-установка

`pip install -e ".[dev]"`. Обычная установка копирует файлы пакета в
`site-packages`. Для разрабатываемого проекта это мучение: правишь исходник —
работает старая копия, пока не переустановишь.

Флаг `-e` вместо копии кладёт файл-указатель. Внутри
`_editable_impl_procurement_analytics.pth` ровно одна строка:

```
C:\Users\ikodxd\claude projexts\procurement-analytics\src
```

При старте Python читает все `.pth` из `site-packages` и каждую строку
добавляет в список папок для поиска модулей. Весь механизм в этом.

Важная оговорка: editable не значит «подхватывает изменения на лету». Python
читает файл в момент импорта, при старте процесса. Правка требует
перезапуска программы, но не переустановки пакета.

## Баг с healthcheck у ClickHouse

Контейнер висел `unhealthy`, хотя снаружи отвечал `200 Ok`.

Порядок разбора, который тут важнее результата:

1. Проверили сервис **в обход** проверки — снаружи 200. Значит сервис исправен,
   врёт healthcheck. Одним действием область поиска сузилась вдвое.
2. Выполнили точную команду healthcheck внутри контейнера: `Connection refused`.
   Текст ошибки принципиален. *Refused* значит «пакет дошёл, на этом порту
   никого нет». *Таймаут* значил бы «пакет не дошёл вовсе» — сеть, фаервол.
   Refused сразу вычёркивает сетевые причины.
3. Перебрали адреса вручную: `127.0.0.1` работает, `::1` и `localhost` — нет.
4. Подтвердили гипотезу логом самого ClickHouse.

Что в логе:

```
Listen [::]:8123 failed: Address family for hostname not supported
Listening for http://0.0.0.0:8123
```

ClickHouse попытался занять порт на всех IPv6-адресах, ядро отказало, и
из-за `listen_try=1` это осталось предупреждением — сервер поехал дальше,
слушая только IPv4. А busybox-wget в Alpine, получив из `/etc/hosts` две
записи для имени `localhost`, выбирает IPv6 первым. Отсюда отказ.

Лечение: в healthcheck вместо `localhost` написали `127.0.0.1`.

Отдельный урок по методу. На шаге 3 была правдоподобная гипотеза, и я сначала
остановился на ней, придумав объяснение «IPv6 в виртуалке выключен». Оно
давало верное лечение, но неверный диагноз: адрес `::1` на loopback как раз
существовал. Гипотезу надо подтверждать источником, а не принимать потому,
что она непротиворечива.

# 27 сентября 2026 — ядро загрузчика

## Разведка API перед кодом

Фикстуры нельзя выдумывать: если придумать формат ответа, весь код и все
тесты окажутся проверкой фантазии. Поэтому сначала факты.

Структура ответа REST v3 (из документации):

```json
{
  "total": 3726048,
  "limit": 50,
  "next_page": "/contract?page=next&search_after=4996100",
  "items": [ ... ]
}
```

Проверка живыми запросами дала ещё четыре факта, которых в документации нет:

| Что проверяли | Результат |
|---|---|
| `/v3/contract` и `/contract` | оба отвечают 401 — оба пути существуют |
| `/v3/graphql` | 404, через GET эндпоинта нет |
| запрос без токена | **401**, заголовок `Www-Authenticate: Bearer realm="api"` |
| запрос с неверным токеном | **403** `{"name":"Forbidden","message":"Access denied"}` |
| заголовки про лимиты | `X-RateLimit-*` и `Retry-After` **отсутствуют** |

Два вывода, которые прямо повлияли на архитектуру.

Первый: 401 и 403 — разные коды за разные причины, но реакция одна, повторять
бессмысленно. Значит в коде это одно исключение, а не два.

Второй, более важный: раз сервер не подсказывает, когда ему станет легче,
паузу после 429 мы обязаны считать сами. Подстройка темпа целиком на нашей
стороне — это и есть обоснование адаптивного лимитера, а не просто красивая
фича.

Ещё деталь: `next_page` — **относительный** путь, не полный URL. При склейке
с базовым адресом это надо учитывать, иначе получится `/v3//contract`.

## Как разложены модули и почему

```
ingest/
├── errors.py    доменные исключения
├── models.py    Page, Batch, CursorState
├── limiter.py   адаптивная конкурентность
├── retry.py     политика повторов
└── state.py     сохранение позиции
```

Главный принцип — ни один модуль выше источника не знает про HTTP. Ни про
httpx, ни про коды ответов. Решения принимаются по типу исключения.

Зачем так: на этапе 3 может понадобиться второй транспорт, и при протёкшей
HTTP-специфике пришлось бы переписывать всё, что лежит выше. Сейчас хватит
новой реализации источника.

## errors.py

Шесть классов. Ключевая мысль — флаг `retryable` живёт **на исключении**, а не
списком кодов внутри `retry.py`:

```python
class SourceError(Exception):
    retryable: ClassVar[bool] = False

class SourceRateLimitError(SourceError):
    retryable: ClassVar[bool] = True
```

Так знание про коды остаётся в одном месте — в реализации источника, которая
их и видит. Слой повторов просто спрашивает «тебя стоит повторять?».

**Термин: ClassVar.** Пометка для проверяющего типы: это атрибут класса, общий
для всех экземпляров, а не поле объекта. Без неё mypy решил бы, что каждому
исключению надо передавать `retryable` в конструктор.

Линтер поймал нарушение PEP 8: имена исключений должны заканчиваться на
`Error`. Изначально было `SourceRateLimited`, стало `SourceRateLimitError`.
Мелочь, но соглашение существует не зря — по имени сразу видно, что это
исключение.

## models.py

**Записи не разбираем.** `RawRecord = dict[str, Any]`, то есть словарь как
пришёл. Соблазн сразу описать схему договора велик, но задача первого этапа —
доставить данные без потерь. Разбирать поля раньше, чем известно, какие нужны,
значит терять то, о существовании чего мы ещё не знаем.

**Три состояния страницы вместо двух.** Это ответ на вопрос из ТЗ «как
отличить конец данных от пустой страницы посреди выдачи»:

```python
class PageKind(StrEnum):
    DATA  = "data"   # есть записи и есть курсор
    EMPTY = "empty"  # записей нет, но курсор есть
    END   = "end"    # курсора нет — выдача кончилась
```

Ошибка, которую это предотвращает: посчитать пустой список концом данных и
молча потерять весь хвост. Признак конца — **отсутствие курсора**, а не
пустота списка.

**Поле `Batch.cursor_after`.** Курсор едет вместе с батчем, а не лежит в общей
переменной. Это не украшение, а механика: так физически невозможно сохранить
позицию раньше, чем батч обработан. Разница между «сохранили после получения»
и «сохранили после обработки» — это разница между потерей данных и их
задвоением при падении. Задвоение переживаемо, записи идемпотентны по id.
Потеря — нет.

**Термин: идемпотентность.** Свойство операции давать тот же результат при
повторном применении. Вставка записи с уже существующим id ничего не меняет —
значит вставка идемпотентна, и повторная обработка батча безопасна.

## limiter.py — самое интересное

### Проблема

`asyncio.Semaphore(4)` создаётся с четырьмя разрешениями и изменению не
подлежит. Метода «а теперь сделай два» у него нет. Адаптивная конкурентность
на голом семафоре невозможна.

### Решение: парковка разрешений

Создаём семафор сразу на **максимум**, а лишние разрешения забираем себе и не
отдаём:

```python
self._sem = asyncio.Semaphore(maximum)
self._parked = 0
```

```python
async def _reconcile(self) -> None:
    want_parked = self._maximum - self._target
    while self._parked < want_parked:
        await self._sem.acquire()   # запарковать ещё одно
        self._parked += 1
    while self._parked > want_parked:
        self._sem.release()         # вернуть в оборот
        self._parked -= 1
```

Уменьшить конкурентность — запарковать больше разрешений. Увеличить — вернуть.
Семафор при этом не пересоздаётся, и уже выполняющиеся запросы не страдают.

Обрати внимание на `await` в первой петле. Если все слоты заняты, парковка
подождёт, пока кто-нибудь освободится. Это правильное поведение: отбирать слот
у запроса, который уже в полёте, нельзя — он-то ни в чём не виноват.

### Уменьшаем множителем, растём шагом

```python
new_target = max(self._minimum, int(self._target * self._decrease_factor))
```

Вниз — вдвое, вверх — по единице. Асимметрия намеренная. При перегрузе надо
уйти вниз быстро, иначе источник продолжит отвечать 429 всё время, пока мы
ползём вниз по единице. Возвращаться наоборот следует осторожно, нащупывая
границу.

### Защита от лавины

Сценарий: восемь запросов в полёте, все восемь получили 429 почти
одновременно. Наивная реализация уменьшит цель восемь раз подряд — 16, 8, 4,
2, 1 — за миллисекунды, хотя перегруз был **один**.

```python
if now - self._last_decrease < self._decrease_cooldown_s:
    return
```

Уменьшение не чаще раза в секунду. Тест `test_burst_of_429_shrinks_only_once`
проверяет ровно это: пять подряд `on_rate_limited()` дают один шаг вниз.

### Монотонные часы

```python
self._last_rate_limit = float("-inf")   # сравнивается с time.monotonic()
```

Не `time.time()`, а `time.monotonic()`. Системное время может прыгнуть назад —
синхронизация по сети, перевод часов, — и тогда вычисленный интервал окажется
отрицательным, а логика восстановления сломается. Монотонные часы только
растут, и годятся ровно для измерения интервалов.

### Фоновый регулятор

Изменение цели и физическая парковка разнесены. `on_rate_limited()` —
синхронный метод: меняет число и ставит флаг. Парковкой занимается отдельная
задача:

```python
async def _regulate(self) -> None:
    while True:
        try:
            await asyncio.wait_for(self._wake.wait(), timeout=self._quiet_period_s)
        except TimeoutError:
            self._maybe_recover()   # тишина — можно расти
        else:
            self._wake.clear()
        await self._reconcile()
```

Зачем разносить: `on_rate_limited()` вызывается из слоя повторов, и он не
должен ждать, пока освободится слот для парковки. Заодно синхронный метод
тривиально тестируется — вызвал, проверил `limiter.target`, никакого
событийного цикла не нужно.

Один цикл делает обе работы. Дождался события — пришёл 429, надо сжаться.
Не дождался за `quiet_period_s` — значит тишина, можно попробовать вырасти.

### Отмена и слот

```python
finally:
    self._in_flight -= 1
    self._sem.release()
```

`release()` синхронный, без `await`, и это принципиально. Блок `finally`
выполняется в том числе во время отмены задачи. Любой `await` внутри него
рискует быть отменён повторно — и тогда слот останется занятым навсегда, а
загрузчик потихоньку встанет.

Тест `test_slot_released_on_cancellation` проверяет это напрямую: берёт
единственный слот, отменяет держателя, убеждается что слот снова доступен.

## retry.py

### Граница с лимитером

Вопрос из ТЗ был «кто реагирует на 429 и в каком порядке». Ответ:

- **retry** решает судьбу **одного** запроса: повторить или сдаться, сколько
  ждать;
- **limiter** решает, сколько запросов идёт **одновременно**.

Оба реагируют на 429, и это не дублирование — они делают разное. Связь
односторонняя: retry сообщает лимитеру факт через узкий протокол.

```python
class RateFeedback(Protocol):
    def on_rate_limited(self) -> None: ...
    def on_success(self) -> None: ...
```

**Термин: Protocol.** Описание требуемой формы объекта без наследования. Любой
класс с этими двумя методами подходит. Благодаря этому `retry.py` не
импортирует конкретный лимитер, и в тестах на его место встаёт заглушка
`FeedbackSpy` в пятнадцать строк.

Отдельное решение: на `SourceUnavailableError` (5xx) лимитер **не** трогаем.
Пятисотка — это авария на той стороне, а не просьба сбавить темп. Сжимать окно
из-за чужой поломки значит наказывать себя. Тест
`test_server_side_unavailable_does_not_shrink_window` это фиксирует.

### Джиттер

**Термин: джиттер.** Случайная добавка к паузе перед повтором.

Зачем он нужен. Восемь корутин получили 429 в один момент. Без джиттера все
восемь подождут ровно одинаково и ударят по источнику снова одновременно —
получат 429 повторно, и так по кругу. Это называется «стадо». Случайность
разносит пробуждения во времени и разбивает синхронность.

Два варианта в коде:

```python
full:  uniform(0, capped)                # разносит сильнее всего
equal: capped/2 + uniform(0, capped/2)   # гарантирует половину паузы
```

По умолчанию `full`. У него есть неприятное свойство — пауза может выйти
почти нулевой, — но именно он лучше всего расталкивает совпавшие повторы.

### Retry-After главнее расчёта

```python
if retry_after_s is not None:
    return min(retry_after_s, policy.max_delay_s)
```

Если сервер сказал, когда приходить, — слушаемся: ему виднее. Но ограничиваем
сверху. Сломанный или недобрый ответ с `Retry-After: 86400` иначе усыпит
загрузчик на сутки. Тест `test_retry_after_is_also_capped`.

У goszakup этого заголовка нет (проверено), но поле оставлено: код не должен
разваливаться, если завтра он появится.

### Находка mypy

```python
exponential = policy.base_delay_s * (2 ** (attempt - 1))
```

mypy ругнулся: функция объявлена возвращающей `float`, а возвращает `Any`.
Причина неочевидная — `2 ** n` у целых чисел типизируется как `Any`, потому
что при отрицательном показателе результат дробный, и точный тип невыводим.
Достаточно сделать основание вещественным: `2.0 ** (attempt - 1)`.

Мелочь, но показательная: строгий режим проверки типов ловит места, где
рассуждение «тут же очевидно число» не выдерживает проверки.

### Дженерики по-новому

Линтер предложил синтаксис из Python 3.12:

```python
async def run_with_retry[T](operation: Callable[[], Awaitable[T]], ...) -> T:
```

Раньше требовалось объявлять `T = TypeVar("T")` отдельной строкой. Теперь
параметр типа пишется прямо в объявлении. Смысл прежний: функция возвращает
ровно то, что вернула переданная операция, каким бы оно ни было.

## state.py

### Атомарная запись

Наивное `open(path, "w")` опасно: если процесс умрёт на середине, на диске
останется обрубок, и при следующем запуске позиция не прочитается.

```python
fd, tmp_name = tempfile.mkstemp(dir=self._path.parent, suffix=".tmp")
with os.fdopen(fd, "w", encoding="utf-8") as fh:
    json.dump(data, fh, ensure_ascii=False, indent=2)
    fh.flush()
    os.fsync(fh.fileno())
os.replace(tmp_name, self._path)
```

Три детали, каждая не случайна.

**`dir=self._path.parent`** — временный файл обязан лежать в той же папке.
`os.replace` атомарен только в пределах одной файловой системы. Через
системную временную папку переименование превратилось бы в копирование, и
атомарность потерялась бы.

**`os.fsync`** — заставляет операционную систему дописать данные на диск, а не
держать их в своём кэше. Без него при выключении питания замена файла
произойдёт, а содержимого в нём не окажется.

**`os.replace`** — подменяет файл одним неделимым действием. В любой момент на
диске лежит либо целиком старая версия, либо целиком новая. Промежуточного
состояния не существует.

### Диск в асинхронном коде

```python
raw = await asyncio.to_thread(self._read_all)
```

Обращение к диску блокирует поток целиком: пока оно идёт, весь событийный цикл
стоит и ни одна другая корутина не исполняется. На одном маленьком файле это
незаметно, но привычка должна быть правильной — на этапе 6 режим отладки
asyncio такие вызовы как раз и выявляет. `to_thread` уносит работу в отдельный
поток и возвращает управление циклу.

### Блокировка

```python
self._lock = asyncio.Lock()
```

Нужна даже в однопоточном asyncio. Между чтением файла и его записью стоит
`await`, а `await` — это точка, где управление уходит другой задаче. Два
сохранения без блокировки успеют перетереть друг друга.

### rest_source.py

Единственное место, где знают про коды HTTP:

| Код | Исключение | Повторять |
|---|---|---|
| 429 | `SourceRateLimitError` | да |
| 401, 403 | `SourceAuthError` | нет |
| 400, 404, прочие 4xx | `SourceRequestError` | нет |
| 5xx | `SourceUnavailableError` | да |
| обрыв, таймаут | `SourceUnavailableError` | да |
| не JSON, нет `items` | `SourceResponseError` | нет |

Один `httpx.AsyncClient` на весь прогон, а не по клиенту на запрос. Внутри
живёт пул соединений: рукопожатия TCP и TLS делаются один раз и
переиспользуются. Клиент на каждый запрос — это оба рукопожатия заново плюс
утечка сокетов, если его забыть закрыть.

Отдельная мелочь про владение: если клиент передали снаружи, источник его не
закрывает. Закрывает тот, кто создал.

Про склейку адресов проверено, а не предположено: httpx одинаково обрабатывает
все четыре сочетания (`/v3` и `/v3/` с `/contract` и `contract`) и всегда даёт
`https://ows.goszakup.gov.kz/v3/contract`. Специальная обработка не нужна.

Тело разбирается через `orjson`, а не стандартный `json`. На этапе 6 будет
замер разницы — пока это просто более быстрый разбор той же формы.

### fixture_source.py

Цепочка страниц строится **из самих данных**, а не из имён файлов: первый файл
отвечает на запрос без курсора, каждый следующий — на тот курсор, который

## pipeline.py

### Порядок фиксации курсора

Самая содержательная часть этапа. Consumers работают параллельно, и батч пятой
страницы может закончиться раньше батча четвёртой. Наивное «обработал —
сохранил курсор» приведёт к тому, что сохранённая позиция укажет за пределы
реально обработанного, и при падении четвёртая страница потеряется молча.

`OrderedCommitter` фиксирует строго по порядку: курсор страницы N сохраняется
только когда обработаны все батчи страниц до N включительно. Инвариант —
сохранённый курсор всегда означает «всё до этого места гарантированно
обработано».

Отдельно отмечу, почему метод `plan` синхронный и не берёт блокировку.
Producer вызывает его **до** того, как первый батч страницы попадёт в очередь,
то есть до того, как хоть один consumer сможет о нём узнать. Точки
переключения задач между объявлением и постановкой в очередь нет, значит нет и
гонки.

Тест `test_cursor_never_runs_ahead_of_processed_pages` проверяет инвариант
напрямую: обработчик специально делает чётные страницы дольше нечётных, чтобы
порядок завершения разошёлся с порядком поступления, а хранилище снимает
слепок обработанного на каждом сохранении.

### Backpressure

Предел очереди — единственное, что не даёт producer выкачать всю сущность в
память, пока consumers отстают. Тест измеряет это буквально: обработчик
держится на событии, и при очереди на два с одним обработчиком producer
успевает взять ровно четыре страницы — одна в работе, две в очереди, на пятой
он встаёт на `queue.put`.

### Отмена

Требование: по сигналу перестать брать новые страницы, дописать начатое,
сохранить позицию, выйти.

Тонкое место — блок `finally`. Корректная остановка сама может быть отменена
повторно, и тогда батч, уже отданный обработчику, оборвётся на середине.
Поэтому:

```python
shutdown = asyncio.ensure_future(self._shutdown(...))
try:
    await asyncio.shield(shutdown)
except asyncio.CancelledError:
    await shutdown   # дождаться защищённой работы
    raise
```

`shield` защищает вложенную задачу от отмены снаружи, но **само ожидание при
этом обрывается сразу**. Поэтому после отмены задачу нужно дождаться явно,
иначе выйдем раньше, чем она допишет. Та же схема применяется к каждому
отдельному батчу в `_handle_protected`.

Щит ставится только на один батч и на остановку. Щит на весь конвейер сделал
бы процесс незавершаемым: он отказывался бы умирать до конца всей выдачи.

Разведены два вида остановки:

- **событие `stop`** (на него вешается SIGTERM) — мягкая: `run` возвращает
  результат с `finished=False` и причиной;
- **отмена задачи** — жёсткая: позиция сохраняется, но `CancelledError`
  пропускается дальше, как и положено.

### Защита от зацикливания

Если источник вернул курсор, который уже встречался, — `CursorLoopError`. Без
неё сломанная пагинация крутила бы одни и те же страницы, пока не кончится
место на диске.

## Две находки, которые стоили времени

### Задача без ссылки может не выполниться

В тесте мягкой остановки я написал `asyncio.create_task(ask_to_stop())` и
заглушил предупреждение линтера `RUF006`. Это было ошибкой: событийный цикл
держит на задачу только слабую ссылку, и без собственной ссылки её может
собрать сборщик мусора до того, как она отработает.

Правило существует не зря. Заглушать предупреждение вместо того, чтобы понять
его, — плохая привычка, и здесь она сразу вышла боком.

### На Windows короткий asyncio.sleep не выполняется

Тест на остановку падал: конвейер проходил все тридцать страниц с задержкой
10 мс каждая за 0.016 секунды. Вместо догадок — измерение:

```
loop._clock_resolution = 0.015625     (GetTickCount64)
10 x sleep(0.01), цикл пустой : 0.1579 с
10 x sleep(0.01), цикл занят  : 0.0002 с
10 x sleep(0.05), цикл пустой : 0.5587 с
```

Причина: разрешение системных часов на Windows — 15.625 мс. Событийный цикл
считает готовыми все таймеры, срок которых наступит в пределах одного
разрешения часов. Пауза в 10 мс всегда попадает в это окно, и если циклу есть
чем заняться (он не блокируется в ожидании), сон не происходит вовсе.

Следствия два. Первое: тесты нельзя строить на коротких паузах — переписал их
на события, теперь момент отмены определяется числом обработанных батчей, а не
часами. Второе, более важное: **замеры пропускной способности на этапе 6
нельзя делать на Windows с короткими интервалами** — цифры будут ложными.
Записал, чтобы не забыть.

## PostgreSQL

### Что положили и почему именно это

Шесть таблиц: `sync_state`, `ingest_run`, `ref_status`, `ref_classifier`,
`app_user`, `saved_filter`. Все маленькие, все меняются по одной строке, всем
нужны транзакции и внешние ключи.

Фактов — договоров и лотов — здесь нет. Их миллионы, они читаются агрегатами
по большим диапазонам, и построчное хранение на них проигрывает.

Про пользователей отдельно: **паролей и токенов в проекте нет**. Пользователь
существует только чтобы владеть сохранёнными фильтрами. Хранить учётные данные
без настоящей задачи аутентификации — лишний риск на пустом месте, и на
собеседовании это защитимая позиция, в отличие от самодельного хеширования.

### Соглашение об именах ограничений

```python
NAMING_CONVENTION = {
    "ix": "ix_%(table_name)s_%(column_0_N_name)s",
    "uq": "uq_%(table_name)s_%(column_0_N_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}
```

Без него PostgreSQL придумывает имена сам, и Alembic при автогенерации не может
сопоставить ограничение в базе с ограничением в коде: он видит незнакомое имя и
предлагает удалить и создать заново. С соглашением имена предсказуемы с обеих
сторон. Второе следствие практичнее: именованное ограничение снимается в
миграции одной строкой, безымянное приходится искать запросом к системным
таблицам.

Тест `test_constraint_names_follow_convention` проверяет это на живой базе.

### Строка с CHECK вместо типа-перечисления

```python
status: Mapped[str] = mapped_column(String(16), default=RunStatus.RUNNING)
__table_args__ = (
    CheckConstraint("status in ('running','succeeded','stopped','failed')", name="status_known"),
)
```

Тип `ENUM` в PostgreSQL выглядит строже, но добавление значения в него — это
`ALTER TYPE`, отдельная миграция с историческими ограничениями на выполнение
внутри транзакции. Строка с `CHECK` даёт ту же гарантию и меняется обычным
`ALTER TABLE`. Гарантия при этом настоящая: тест
`test_unknown_status_is_rejected_by_database` вставляет статус «выдумка» и
ожидает `IntegrityError` от базы, а не от Python.

### JSONB, а не JSON

`JSON` в PostgreSQL — это текст с проверкой синтаксиса при записи. `JSONB`
хранится в разобранном двоичном виде, поддерживает операторы поиска и индексы
GIN. Тест `test_jsonb_payload_is_queryable` ищет по полю внутри документа —
именно ради этого тип и выбран.

### Находка в типизации SQLAlchemy

```python
row = await session.scalar(select(SyncState).where(...))   # тип: Any
```

`session.scalar()` объявлен возвращающим `Any`, и строгий mypy поймал это на
возврате из функции. Хуже другое: `Any` расползается дальше — всё, что с этим
объектом делают потом, тоже перестаёт проверяться. Правильная форма:

```python
found = await session.scalars(select(SyncState).where(...))
row = found.first()     # тип: SyncState | None
```

Мелочь, которая иначе тихо выключила бы проверку типов на половине модуля.

### Только select()

`session.query()` в проекте не используется нигде. Это не вкусовщина: стиль
остался от SQLAlchemy 1.x, идёт внутри библиотеки отдельным путём и в
асинхронном режиме не работает вовсе.

## Alembic

Шаблон взял `async` — тот, что кладёт классический `alembic.ini`. Есть ещё
`pyproject_async`, который прячет настройки в `pyproject.toml`, но `alembic.ini`
встречается в рабочих проектах чаще, и разбираться в нём придётся именно с ним.

Три правки в `env.py`, каждая осмысленная.

**Адрес базы из настроек, а не из ini.** Иначе он записан в двух местах, и
однажды они разойдутся. Заодно пароль не лежит в репозитории.

**Но с возможностью переопределить снаружи:**

```python
if not config.get_main_option("sqlalchemy.url", None):
    config.set_main_option("sqlalchemy.url", get_settings().postgres.dsn)
```

Без проверки `if not` тесты на testcontainers накатили бы миграции **в базу
разработчика** вместо своей временной. Это не гипотетическая беда: они
поднимают чистый контейнер, подставляют его адрес и вызывают `upgrade`, и
жёсткая подстановка из настроек увела бы их в рабочую базу.

**compare_type и compare_server_default.** Без них Alembic не заметит смену
типа колонки или значения по умолчанию и молча пропустит изменение.

другой системе или в архиве. Пересоздал с латинским `initial schema`. Сообщения

Это ответ на вопрос «а точно ли миграция описывает то, что в моделях». Команда
сравнивает модели с реальной базой и молчит, только если расхождений нет. Добавил
как `make check-drift`.

## ClickHouse

### Движок

`ReplacingMergeTree(last_update_date)`. Записи ревизируются: у договора меняются
статус, сумма, сроки. Обновлять строку на месте ClickHouse не умеет и не должен —
загрузчик просто вставляет новую версию, а движок при слиянии кусков оставляет
ту, у которой больше значение версии.

### Что можно и чего нельзя класть в ключ сортировки

Дедупликация идёт по **полному ключу сортировки**. Отсюда два жёстких правила.

`id` в ключе быть **обязан** — иначе две разные записи одного заказчика
схлопнутся в одну.

Изменяемых полей в ключе быть **не может**. Положи в ключ статус — и при
ревизии ключ станет другим, движок сочтёт старую и новую строки разными
записями, схлопывания не произойдёт, данные тихо задвоятся. Именно тихо: ошибки
не будет, просто цифры станут больше.

### Ключ партиционирования обязан быть неизменным

Тут я ошибся в формулировке, и тест меня поправил. Разберу честно, потому что
сама ошибка поучительнее правильного ответа.

Я написал тест с утверждением: если две версии записи попали в разные партиции,
`SELECT ... FINAL` вернёт две строки, потому что дедупликация работает только
внутри партиции. Тест упал: вернулась одна.

Проверка вместо догадки:

```
строк без FINAL : 2      <- физический дубль остался
строк с FINAL   : 1      <- при чтении склеился
партиций        : 2
do_not_merge_across_partitions_select_final = 0
```

Настоящая картина такая. **Физическое** слияние идёт только внутри партиции:
даже принудительный `OPTIMIZE TABLE ... FINAL` дубль через границу партиций не
уберёт — никогда, ни при каких условиях. А `SELECT ... FINAL` при чтении
склеивает и через партиции, потому что настройка
`do_not_merge_across_partitions_select_final` по умолчанию равна нулю.

Вывод меняется, и в лучшую сторону по точности: беда от изменяемого ключа
партиционирования **не в неверных цифрах**, а в том, что таблица растёт без
предела и каждый запрос навсегда обязан платить за `FINAL`. Схлопнуть эти дубли
физически невозможно в принципе.

Это закреплено тестом
`test_duplicates_in_different_partitions_never_collapse_on_disk`.

### И отсюда — проблема лотов

У договора неизменная дата есть: `crdate`. Партиционируем по `toYYYYMM(crdate)`.

У лота её нет — только `lastUpdateDate` и `indexDate`, обе меняются. Требование
«партиционировать по месяцу» для лотов невыполнимо честно: любая помесячная
схема на изменяемой дате означает вечно растущую таблицу.

Решение: лоты партиционируются по диапазону `id` — он стабилен. Помесячное
партиционирование станет возможно на третьем этапе, когда появится дата
объявления из связанной сущности `TrdBuy`.

Это лучше, чем сделать «как просили» и получить схему, которая тихо ломается.

### Деньги — Decimal, не Float

`Float64` хранит 0.1 приближённо. Сумма миллиона договоров разойдётся с
бухгалтерией в последних разрядах, и найти это потом крайне неприятно. Выигрыша
в скорости на наших объёмах нет. Тест
`test_money_columns_are_decimal_not_float` не даёт однажды «оптимизировать»
это обратно.

Полные условия и таблицы — в [docs/bench/order_by.md](bench/order_by.md).

**Метод.** 20 млн записей плюс 2 млн ревизий, 60 тысяч заказчиков, 150 тысяч
поставщиков, четыре варианта ключа, одни и те же данные, четыре типовых

Данные генерировал сам ClickHouse из `numbers()`. Гнать двадцать миллионов

**Главный результат.** Решает первая колонка ключа, остальные почти не влияют:

префиксу ключа; фильтр по второй колонке пропуск не включает.

**Побочная находка, которая объясняет «0.5 млн».** Почему точечный запрос по
одному заказчику из шестидесяти тысяч читает полмиллиона строк? Посчитал:

```

```

вывод: **много партиций — это не бесплатно**. Помесячное партиционирование за
десять лет даст 120 партиций и удвоит нижнюю границу чтения для всех запросов
без фильтра по дате.

**Ключ сортировки не помогает запросам по дате.** Все четыре варианта показали

не дал ничего: партиции уже сделали всю работу.

**Отсортированные данные лучше сжимаются.** Вариант A занимает 992.9 МБ против

признаю честно: решать его, если понадобится, надо проекцией, а не сменой
ключа.

## FINAL: что это и почему на него нельзя опираться

Воспроизводится скриптом `scripts/demo_final.py`.

**Что происходит.** Вставили договор, потом его ревизию. На диске лежат обе
строки — движок не трогает данные при вставке, только при слиянии кусков.

```
строк без FINAL : 2      кусков на диске : 2
строк с FINAL   : 1
```

`FINAL` — это указание склеить версии **при чтении**, на лету. Он ничего не
меняет на диске.

**Главная ловушка.** Без `FINAL` агрегат считается по всем версиям:

```
SELECT sum(contract_sum) без FINAL : 350000.00   <- сложились обе версии
SELECT sum(contract_sum) с FINAL   : 250000.00   <- верно
```

Ошибки нет, исключения нет. Просто неверная цифра в отчёте.

**Когда происходит слияние.** Фоновый пул планирует слияния сам, исходя из
размеров и числа кусков. Никаких гарантий по времени нет. Более того, есть
жёсткий потолок: `max_bytes_to_merge_at_max_space_in_pool` на этой машине равен
150 ГиБ, и куски крупнее уже не сольются никогда. Наблюдение из эксперимента: у
таблицы `contracts_a` после дозаливки ревизий осталось 132 активных куска, и к
концу прогона фоновые слияния их так и не догнали.

**Чего стоит FINAL.** Замер на 20 млн строк с 2 млн ревизий, 132 куска:

```
запрос без FINAL : 172 мс   (ответ неверный)
запрос с FINAL   : 1300 мс  (ответ верный)
цена корректности: x7.5
```

**Почему на FINAL нельзя опираться в проде.** Три причины, каждая сама по себе
достаточна:

1. Цена. Семь с половиной раз — это не накладные расходы, это другой класс
   отзывчивости. На витрине под интерфейсом такое не живёт.
2. Цена непредсказуема. Она зависит от числа несклеенных кусков, а оно зависит
   от того, когда фоновый пул успел поработать. Один и тот же запрос сегодня
   отвечает за 200 мс, а сразу после большой загрузки — за две секунды.
3. Его легко забыть. `FINAL` — это слово в запросе. Забыл в одном месте из
   двадцати — получил тихо неверную цифру, без всяких признаков ошибки.

**Что делать вместо.** Три подхода, в порядке предпочтения:

- **Агрегаты, устойчивые к дублям.** `argMax(contract_sum, last_update_date)`
  сгруппированное по `id` даёт верный ответ без `FINAL` и без надежды на
  слияния.
- **Витрины.** Считать агрегаты заранее, один раз, при загрузке — там `FINAL`
  допустим, потому что это фоновая работа, а не запрос пользователя. Этим
  займётся третий этап.
- **`OPTIMIZE ... FINAL` по расписанию на конкретной партиции.** Годится для
  свежей партиции, куда только что лили данные. Гонять на всей таблице нельзя:
  это перезапись всех данных с нуля.

## Приведение типов

Источник отдаёт JSON, где всё либо строка, либо число, либо null. ClickHouse
ждёт DateTime, Decimal и UInt. Между ними нужен слой, и главный вопрос к нему —
что делать с пропущенным значением.

Принятое решение: **пропуск не повод терять запись**. Пустое поле превращается
в заметное значение по умолчанию, запись проходит дальше, а факт пропуска ловят
проверки качества. Молча уронить запись хуже: она исчезнет, и никто не узнает.

Отдельно про даты. У `crdate` нет варианта «пусто»: она входит в ключ
партиционирования. Отсутствующая дата становится `1970-01-01`, и такие записи
оседают в партиции `197001` — не теряются и сразу заметны. Отдельная проверка
считает их долю.

И мелочь, которая на деле не мелочь:

```python
Decimal(0.1)        # 0.1000000000000000055511151231257827
Decimal(str(0.1))   # 0.1
```

Приведение к Decimal идёт через `str`, иначе двоичная погрешность float
переезжает в тип, который заводили ровно чтобы её не было.

## Защита имён вместо подавления предупреждения

Линтер выдал пять предупреждений S608 о возможной SQL-инъекции в проверках
качества. Имена таблиц и колонок нельзя передать параметром запроса — их
приходится подставлять в текст.

Можно было поставить `# noqa` и забыть. Вместо этого появилась настоящая
проверка:

```python
_IDENTIFIER = re.compile(r"^[A-Za-z_][A-Za-z0-9_]*$")

def safe_identifier(value: str, *, what: str = "идентификатор") -> str:
    if not _IDENTIFIER.match(value):
        raise ValueError(f"{what} {value!r} не похож на безопасное имя")
    return value
```

Это не перестраховка. Суффикс временной таблицы при бэкфилле собирается из
параметров запуска DAG, а туда попадает что угодно. Теперь `noqa` рядом с
запросом честен: подставляется только проверенное.

Одно место из шести оказалось вообще не про идентификатор — там имя таблицы
было **значением** в условии `WHERE table = ...`. Его переписал на параметр
запроса, и предупреждение ушло само.

## Два способа публиковать данные

Это ключевое решение этапа.

**Прямая вставка** — для инкрементальной синхронизации. Изменившиеся записи
приходят вперемешку из любых месяцев, и заранее неизвестно, какие партиции они
затронут. Повторная вставка не ломает результат, но дубли исчезнут только при
слиянии, а до тех пор запросы обязаны считаться с ними.

**Подмена партиции** — для помесячного бэкфилла:

```sql
ALTER TABLE contracts REPLACE PARTITION '202403' FROM contracts_staging_202403
```

Месяц целиком собирается во временную таблицу и въезжает в боевую одним
неделимым действием. Повторный запуск за тот же месяц даёт ровно тот же
результат — данные не задваиваются даже физически, и FINAL для них не нужен.

Это **сильнее**, чем полагаться на ReplacingMergeTree: там дубли исчезают
когда-нибудь, а здесь не возникают вовсе.

У способа есть жёсткое условие: партиция заменяется **целиком**. Значит месяц
обязан быть выкачан полностью. Залить половину и подменить — потерять вторую.
Отсюда порядок шагов, и он не произвольный:

1. создать временную таблицу той же структуры;
2. выкачать месяц целиком;
3. схлопнуть ревизии внутри неё;
4. прогнать проверки качества;
5. только при успехе подменить партицию;
6. убрать временную таблицу.

Проверка на шаге 4 стоит **до** публикации не для красоты схемы: плохой месяц
не доезжает до пользователей вовсе.

Отдельная деталь: бэкфилл работает со **своим временным состоянием**, а не с
общим `sync_state`. Иначе он сдвинул бы курсор инкрементальной синхронизации, и
та после него пропустила бы свежие изменения.

## Проверки качества на SQL

Требовалось проверять долю пустых полей, суммы вне диапазона, дубли по id и
расхождение количества с ответом API.

Первая мысль — накапливать счётчики в Python по мере прохождения батчей. Мысль
плохая: множество идентификаторов для поиска дублей на миллионах записей — это
гигабайты памяти ради того, что ClickHouse считает одним `uniqExact`. Данные
уже лежат в таблице, считать по ним надо там же.

Что проверяется:

| Проверка | Уровень | Порог |
|---|---|---|
| таблица не пуста | fail | больше нуля |
| дубли по id | fail | 0 |
| пустых в обязательном поле | fail / warn | 5% / 1% |
| сумма вне диапазона | fail | 0% |
| не разобралась дата | warn | 1% |
| расхождение с `total` источника | fail | 1% |

**Два уровня строгости** — тоже решение, а не украшение. `fail` останавливает
заливку: данные заведомо испорчены. `warn` пропускает, но остаётся в журнале.
Разница важна практически: пайплайн, который падает от каждого подозрительного
числа, быстро отключают, и тогда не работает ни одна проверка.

## Инкрементальная синхронизация: почему по знаку, а не по курсору

Курсор отмечает, до какого места в выдаче мы дошли. Для первичной выкачки этого
достаточно. Но записи ревизируются: договор, изменившийся вчера, лежит где-то в
середине уже пройденного списка, и курсор о нём ничего не скажет.

Догонять изменения надо по дате последнего изменения — по водяному знаку.

Порядок такой же, как у бэкфилла, и это не совпадение: проверки качества стоят
между загрузкой и публикацией в обоих случаях. Разница только в способе
публикации.

Водяной знак двигается **после** публикации, а не до. Та же логика, что с
курсором в загрузчике: упасть между загрузкой и сдвигом значит перезабрать
данные повторно, а сдвинуть раньше — потерять их навсегда.

## Синтетический источник

Токена goszakup всё ещё нет, а бэкфилл за три года прогнать надо: без этого
нельзя ни измерить пропускную способность, ни доказать идемпотентность.
Пятнадцати записей в фикстурах для этого не хватит.

Появился `SyntheticSource`: генерирует правдоподобную выдачу за заданный месяц.
Набор полей повторяет схему API, значения выдуманы детерминированно, БИН
начинаются с девятки — такие не выдаются. Источник реализует тот же протокол,
что и сетевой, и подставляется без единой правки в конвейере.

Детерминированность здесь не прихоть: без неё проверка идемпотентности
бессмысленна. Одна и та же страница обязана быть одной и той же при каждом
обращении, поэтому генератор случайных чисел создаётся на каждую запись от её
номера, а не один на весь прогон.

## Три пойманных бага

### Цикл по месяцам не заканчивался

Дымовой прогон январь-февраль прошёл. Трёхлетний упал с `MemoryError`.

Виновата была попытка посчитать следующий месяц через `divmod`:

```python
year, month = divmod(current.year * 12 + current.month, 12)
current = date(year, month + 1, 1) if month != 0 else date(year - 1, 12, 1)
```

Для декабря 2023: `divmod(24288, 12) = (2024, 0)`, ветка `month == 0` даёт
`date(2023, 12, 1)` — тот же месяц. Цикл крутится, список растёт, память
кончается.

Переписал на очевидную форму с явным переносом года и добавил тест именно на
границу декабря. Урок простой: проверять надо границы, а не середину.

### Водяной знак молча не сохранялся

`set_watermark` делал `UPDATE ... WHERE source = ... AND entity = ...`. Строки в
`sync_state` ещё не существовало: бэкфилл ведёт своё временное состояние и сюда
ничего не пишет. `UPDATE` менял ноль строк, ошибки не возникало, знак не
сохранялся.

Первый прогон синхронизации выглядел нормально. Поймалось только вторым: он
снова опубликовал те же 2000 записей вместо нуля.

Исправлено на `INSERT ... ON CONFLICT DO UPDATE`. Урок: операция, которая
«ничего не нашла», обязана либо создать, либо пожаловаться. Молчать она не
должна.

### Дубль не создавался одной вставкой

Тест на проверку дублей вставлял две строки с одним id **одной командой** и
ожидал двух строк в таблице. Получил одну.

Проверка вместо догадки:

```
одна вставка двух строк  -> строк: 1
две отдельные вставки    -> строк: 2, кусков: 2
```

Оказалось: строки с одинаковым ключом сортировки, пришедшие одной вставкой,
схлопываются уже при формировании куска. Дубль возникает только **между
разными кусками**, то есть между разными вставками. Тест переписан.

Полезное побочное знание: одна большая вставка лучше многих мелких не только
по накладным расходам, но и потому, что часть дублей схлопывается сразу.

## Airflow

Версия 3.3.2 — проверил список тегов образа, а не взял из памяти. В третьей
версии архитектура другая, и это влияет на compose:

- `api-server` вместо `webserver`;
- `dag-processor` вынесен в отдельный процесс: планировщик больше не исполняет
  чужой код у себя. Без этого сервиса новые DAG-и просто не появятся;
- аутентификация через SimpleAuthManager, и для локального стенда есть
  `AIRFLOW__CORE__SIMPLE_AUTH_MANAGER_ALL_ADMINS` — вход без пароля.

Имена настроек проверял прямо в образе (`airflow config list`), а не по памяти:
`AIRFLOW__API_AUTH__JWT_SECRET` существует, и это не то же самое, что было во
второй версии.

### Метаданные в отдельной базе

Airflow держит свои метаданные в собственном PostgreSQL, а не рядом с данными
проекта. Их жизненные циклы не связаны: снести метаданные Airflow можно, не
трогая состояние загрузчика.

### Зависимости в образ ставятся выборочно

Соблазн был поставить проект целиком через `pip install -e .`. Не стал: в
зависимостях FastAPI и uvicorn, которые Airflow не нужны, а конфликтовать с его
пинами могут. В образ ставятся только библиотеки, нужные заданиям, а сам код
подключается через `PYTHONPATH` — каталог `src` смонтирован томом, и правка
видна без пересборки.

### Логики в DAG-ах нет

Это самое важное решение в разделе. Задача вызывает `backfill_month` из
`procurement.jobs.backfill` — ту же функцию, что запускается из командной
строки. В DAG остаются только расписание, повторы и передача месяца.

Почему так. Логика внутри DAG отлаживается единственным способом: поднять
планировщик и читать его логи. Её нельзя ни прогнать локально, ни покрыть
тестами. Вынесенная в обычные функции, она тестируется как любой другой код —
что и сделано, 11 интеграционных тестов на задания.

### Один запуск — один месяц

Бэкфилл сделан как `@monthly` DAG с `catchup=True`, а не как одна задача с
циклом по месяцам. Разница практическая: Airflow сам держит очередь, сам
повторяет упавшие месяцы и показывает, какие уже сделаны. При цикле внутри
одной задачи падение двадцатого месяца потребовало бы перезапуска всех
тридцати шести.

Месяц берётся из `data_interval_start`, а не из «сегодня». Это то, что отличает
воспроизводимый бэкфилл от невоспроизводимого: перезапуск запуска за март 2023
года всегда грузит март 2023 года, когда бы он ни случился.

## Проверка перед проектированием

Первый запрос этапа — рекурсивный обход дерева классификатора. От того, умеет
ли ClickHouse рекурсивные CTE, зависело устройство всего слоя: если не умеет,
дерево пришлось бы разворачивать в PostgreSQL и отдавать в ClickHouse готовую
плоскую таблицу соответствий.

Проверка заняла один запрос:

```sql
WITH RECURSIVE t AS (SELECT 1 AS n UNION ALL SELECT n+1 FROM t WHERE n < 5)
SELECT groupArray(n) FROM t
-- [1,2,3,4,5]
```

Умеет. Значит оба варианта запроса будут честно сопоставимы, а не «в одной
базе запрос, в другой обходной манёвр».

## Что пришлось добавить в данные

**Код товарной позиции у лота.** Без него не посчитать отклонение цены от
медианы: сравнивать надо внутри одной позиции, а не по всем лотам подряд. В
схеме API у лота это `enstruList` — список. В таблицу кладётся один код,
первый из списка, и это записано в схеме как сознательное упрощение: аналитике
нужна одна позиция на лот, иначе любая сумма по категории задвоится на лотах с
несколькими кодами.

**Дерево классификатора.** Настоящий ЕНС ТРУ отдаётся только по токену, поэтому
дерево синтетическое: 20 разделов, 4620 узлов, 4000 листьев, четыре уровня.
Форма повторяет реальную — код собирается из уровней через точку (07.3.2.041).

Справочник кладётся в **обе** базы. В PostgreSQL он источник истины с внешними
ключами. В ClickHouse — копия рядом с фактами: соединение фактов со
справочником через границу двух баз ClickHouse не умеет, а тянуть миллионы
строк в приложение ради соединения бессмысленно.

## Копия фактов в PostgreSQL

Утверждение «в ClickHouse быстрее» без цифр — мнение. Чтобы сравнить, те же
данные должны лежать в обеих базах.

Два решения, каждое влияет на честность сравнения.

**Данные не генерируются заново, а переливаются из ClickHouse.** Так снимается
возражение «а данные точно одинаковые» — они буквально одни и те же. Перелив
1.8 млн договоров занял 29.6 с, лотов 20.7 с.

**PostgreSQL получил индексы и ANALYZE.** Сравнивать колоночную базу с
неиндексированной строчной нечестно: любой инженер, положив эти данные в
PostgreSQL, индексы бы создал. Без свежей статистики планировщик выбирает планы
вслепую, и замер показывал бы не базу, а невезение.

Схема названа `bench` и существует только ради замеров. Боевой код в неё не
ходит, и архитектурное утверждение «факты не в PostgreSQL» остаётся верным.

## Шесть запросов

Каждый в двух вариантах, все лежат файлами в `sql/` — их можно читать, править
и запускать отдельно от кода.

**Свёртка по дереву классификатора.** Рекурсивный CTE идёт от листьев вверх,
таща за собой исходный лист, и останавливается на нужном уровне. Соблазн
отрезать хвост кода строкой велик, и я его не стал реализовывать: структура
кода — свойство конкретного классификатора, а связь родитель-потомок хранится
явно. Запрос, опирающийся на форму строки, сломается на первом же справочнике
с другой нумерацией.

**Доля поставщика в закупках заказчика.** `sum(sum(...)) OVER (PARTITION BY)`
читается странно, но смысл прямой: внутренний `sum` считает агрегат группы,
внешний — окно поверх уже посчитанных групп. Обычной группировкой это не
получить: `GROUP BY` даёт один уровень детализации, а нужны два в одной строке.
Подзапрос с повторным соединением решил бы задачу, но прочитал бы таблицу
дважды.

**Отклонение цены от медианы.** Считается цена за единицу, а не сумма лота: лот
на тысячу пачек бумаги и лот на одну пачку по сумме сравнивать бессмысленно.
Медиана, а не среднее: среднее утаскивается вверх единичным дорогим лотом, и
тогда «отклонение от среднего» покажет отклонение от выброса. Позиции меньше
чем с 30 лотами отброшены — медиана по трём наблюдениям это не медиана, а
случайное число.

**Помесячная динамика через LAG.** Альтернатива — соединить таблицу саму с
собой по «месяц минус один», и она хуже сразу по двум причинам: соединение
дороже, и пропущенный месяц молча выпадет из выборки вместо того, чтобы
показать разрыв.

**Индекс Херфиндаля.** Сумма квадратов долей в процентах, от 10000/N до 10000.
Возведение в квадрат нужно, чтобы крупные доли весили непропорционально
больше: это и отличает концентрацию от простого числа участников. Оконные
функции идут в два этажа, потому что вложить окно в окно нельзя: сначала доля
каждого поставщика, потом накопительная сумма долей по убыванию.

**Gaps and islands.** Приём классический и на первый взгляд странный: из
порядкового номера месяца вычитается номер строки в окне. Пока месяцы идут
подряд, обе величины растут на единицу и разность постоянна — она и служит
меткой отрезка. Появился пропуск — номер месяца прыгнул, номер строки нет,
разность изменилась. Месяц переводится в сплошной счётчик `год * 12 + месяц`
намеренно: по номеру месяца внутри года граница декабря дала бы ложный разрыв.

## Главный урок этапа: сверять результаты, а не только время

Скрипт замеров сверяет результаты двух баз построчно. Это не перестраховка:
быстрее всего работает неправильный ответ.

При первом прогоне **три запроса из шести дали разные результаты**, и ни разу
причиной не были сами базы.

### Медиана считается по-разному

```
выборка [1, 2, 3, 4]
  PG percentile_cont        -> 2.5
  PG percentile_disc        -> 2.0
  CH quantileExact          -> 3.0
  CH quantileExactInclusive -> 2.5
```

`percentile_cont` **интерполирует**: возвращает 2.5, числа которого в данных
нет. `quantileExact` возвращает настоящий элемент выборки. Обе функции
называются медианой, определения разные. Соответствие даёт
`quantileExactInclusive`.

Обычный `quantile` брать нельзя вовсе — он приближённый, через резервуарную
выборку, и расхождение было бы не из-за баз, а из-за метода.

### lagInFrame — не синоним lag

На первой строке, где предыдущей нет, PostgreSQL возвращает NULL, а ClickHouse
— значение по умолчанию для типа, то есть ноль.

Разница не косметическая. Ноль означал бы «в прошлом месяце закупок не было»,
что неправда: прошлого месяца в данных просто нет. Отчёт с нулём вместо пропуска
показал бы падение на 100% там, где данных нет вообще.

Лечится третьим аргументом: `lagInFrame(toNullable(total), 1, NULL)`.

### ORDER BY с LIMIT без однозначного порядка

Индекс Херфиндаля округляется до целого, и на равномерных синтетических данных
сотни заказчиков получают одно и то же значение — 56. `ORDER BY hhi DESC LIMIT
20` выбирает из них произвольные двадцать, и каждая база выбирает свои.

Это единственный из трёх случаев, который был **настоящей ошибкой в запросе**.
Недетерминированный запрос невоспроизводим даже в одной базе: тот же запрос
завтра может вернуть другие строки. Сортировка с `LIMIT` обязана быть
однозначной; добавлен `customer_bin` вторым ключом.

Остальные два — разница диалектов, о которой надо знать.

## Ещё одна ловушка PostgreSQL

Запрос про медиану упал:

```
function round(double precision, integer) does not exist
```

`round` с двумя аргументами в PostgreSQL определён **только для numeric**.
`percentile_cont` возвращает `double precision`. Раздражающая мелочь, но
показательная: она ловится только запуском, никакой линтер SQL этого не
скажет.

## Тесты на правильность

Скорость меряет скрипт, а тесты проверяют, что запросы дают верный ответ. Набор
данных крошечный и подобран так, чтобы результат считался руками: иначе тест
проверял бы, что запрос выдаёт то же, что выдавал вчера, а не то, что должен.

Десять тестов, из них три показательных:

- **Доля поставщика.** Два поставщика на 750 и 250 — доли обязаны быть 75 и 25,
  и в сумме сто.
- **Gaps and islands через границу года.** Ноябрь, декабрь, январь — один
  отрезок, а не два. Именно здесь ломается наивный вариант, считающий разницу
  по номеру месяца внутри года.
- **LAG на первом периоде.** Возвращает NULL, а не ноль. Тест закрепляет ровно
  тот случай, на котором разошлись базы.

Запросы берутся из тех же файлов в `sql/`, что идут в замеры и в документацию.
Копии в тесте не было бы смысла: разошлись бы через неделю.

## Честно про данные

Данные синтетические и распределены равномерно: поставщики назначаются
договорам случайно. Из-за этого индекс Херфиндаля у всех заказчиков выходит
около 56 при максимуме 10 000 — закупки выглядят предельно
неконцентрированными.

На настоящих данных картина будет другой. Запрос от этого не меняется, а замер
скорости зависит от объёма и кардинальности, а не от правдоподобия
распределения. Но выдавать эти 56 за вывод о рынке было бы обманом, и в
документе это сказано прямо.

Формулировки в выводах фактические. Высокий индекс концентрации — результат
расчёта по суммам договоров. Причины бывают любые: единственный поставщик на
рынке, специфика предмета закупки, размер заказчика. Выводов о
добросовестности из этих чисел не следует, и в проекте они не делаются.
